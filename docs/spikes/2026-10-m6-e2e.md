## Defects found
1. **Another user's version id on the subtitle routes answers 500** (minor; fixed in 8ac75f7, re-run R2). Repro: as alice,
   `GET /Videos/{Gladiator}/{a version id of dev}/Subtitles/2000/0/Stream.vtt` with alice's token -> 500,
   `InvalidOperationException: Sequence contains no matching element` at `SubtitleEncoder.GetSubtitles`.
   `SubtitleRequestFilter.Refuse` finds the version in the (global) `VersionRegistry`, the caller is not anonymous, the
   index is 2000, so it lets the request through; Jellyfin then looks the version up among alice's own sources and
   throws. Clients send their own version ids, so this needs a mistaken or hand-made request; an unknown id that is not in the registry behaves the same as
   on stock Jellyfin (500). Suspected file: `src/Jellyfin.Plugin.Currents/Integration/SubtitleRequestFilter.cs`
   (refuse with 404 when the registered version belongs to another user).
2. **Built-in text subtitles before a trailing cover-art stream stay in PlaybackInfo on over-limit versions** (fixed in 1005bc1, re-run R4-R5). Repro:
   *Gladiator* version `1f2c815e…` (44.6 GB, default limit 15), play once so the probe runs (`Probed a version of
   "tt0172495" in 1.1 s`), then `GET /Items/{id}/PlaybackInfo` as `dev`: streams end `6 subrip, 7 subrip, 8 subrip,
   9 EmbeddedImage (mjpeg), 2000 webvtt`. `VersionSourceBuilder.HideBuiltInTextSubtitles` (playback branch) walks back
   from the end, skips external streams, and stops at the first stream that is not a built-in text subtitle; the
   MKV cover art (`EmbeddedImage`) is that stream, so nothing is removed. The web player then lists the three `SUBRIP`
   tracks; picking one would get a 404 from `SubtitleRequestFilter` (checked: indexes 6-8 -> 404), so no whole-file
   extraction starts, but the subtitle silently fails. MKV remuxes commonly carry a cover-art attachment last.
   Suspected file: `src/Jellyfin.Plugin.Currents/Streams/VersionSourceBuilder.cs` (`HideBuiltInTextSubtitles`: also
   step over `EmbeddedImage` streams, which ffmpeg never maps, if that keeps the audio/video positions intact).

Finding: with the item id as the source, Jellyfin's `SubtitleEncoder.GetSubtitles` throws "Sequence contains no matching
element" for a downloaded index. It does not resolve the id through the decorated `GetMediaSource`, so 1.0.0 failed the
same way (confirmed by running the 1.0.0 build on this stack). The guard now maps the item id like the decorator (the
built-in-index refusal above proves it picked the over-limit first version), but the downloaded-subtitle request still
ends in Jellyfin's own 500. Clients that build subtitle URLs from the version ids Currents lists are unaffected.
